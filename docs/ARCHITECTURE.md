# Architecture

A New Year ritual website: people write what they want to leave in the old year, pay a small amount, and watch their paper burn in a shared digital fire (on the site and on a YouTube live stream). Optional: a wish for the next year, kept and opened live next New Year's Eve.

The brand name is **not final**. Never hard-code a brand name or domain: read it from `site/config/site.json` (`brand.*`, `domain`).

Languages: Armenian (`hy`, default, at `/`), English (`/en/`), Russian (`/ru/`).

## Money rules

- Every price is an integer in AMD. Prices live in `site/config/site.json` (frontend display) **and** in the `products` table (source of truth for charging). The server never trusts a price from the browser.
- **One price (since migration 0008): everything costs 500 AMD.** Only two products are sold:

  | code | price | what |
  |---|---|---|
  | `burn` | 500 | A paper burned in the fire |
  | `light` | 500 | A light on the map ("Light up Armenia") |

  **Since migration 0013 only `light` can be ordered**: one payment (500 AMD) buys a plot with its room **and exactly one wish burned in the fire** (`POST burn-wish`, see "Wish in the fire"). No separate payment for burning, no second wish for the same light. Every paper product (`burn`, `burn_wish`, `gift`, `midnight`) is retired for new orders: `create-order` answers `400 PRODUCT_RETIRED`. Existing paper orders keep working (start-payment, bank callbacks, the fire feed); the `burn` row stays `active` for them.

  `burn_wish`, `gift`, `midnight` and `light_big` are **no longer sold**: their rows stay in `products` with `active = false` (old orders reference them). `create-order` and `start-payment` answer `400 PRODUCT_UNAVAILABLE` for an inactive product. Their code paths (wish, recipient, big light) still exist but are unreachable while the rows are inactive.
- **20% of every paid amount** goes to the New Year gift fund for children in Armenian orphanages (100 AMD per 500 AMD order). It is recorded per payment in `gift_ledger` at the moment the payment is confirmed, rounded down to whole AMD.
- We are a for-profit company and say so. The 20% is a choice we made, not the business model.

## Security rules (non-negotiable)

1. An order becomes `paid` **only** inside the database function `confirm_payment(...)`, called by an Edge Function after it verified the payment with the bank server-to-server (or with the provider's signature). The browser can never mark anything paid.
2. `confirm_payment` is idempotent: the same provider payment can't be counted twice, and the amount must equal the order amount.
3. All tables have RLS enabled with **no** policies for `anon`/`authenticated`. The browser reads data only through `SECURITY DEFINER` RPCs that return safe, public fields, or through Edge Functions.
4. Order codes are random, unguessable (16 chars, base32 lowercase without ambiguous letters). The code is the capability to view one's own order.
5. Papers are moderated before they can appear publicly. Text is shown on the public fire only if the buyer allowed it **and** moderation status is `approved`.
6. Rate limits per IP hash (salted SHA-256, never the raw IP) for order creation, waitlist, blogger applications, room edits and room warmth/visits.
7. Secrets only in Supabase function secrets / Vercel env, never in the repo.

## Edge Functions (base `https://<ref>.supabase.co/functions/v1/`)

All responses are JSON with CORS for the site origins (`ALLOWED_ORIGINS` secret, comma-separated; when empty, only the origin of `SITE_URL`). `http://localhost:*` is allowed only when `ALLOW_LOCALHOST=1`, and `*.vercel.app` previews only when `ALLOW_VERCEL_PREVIEWS=1`.
Error shape: `{ "error": { "code": "TEXT_TOO_LONG", "message": "..." } }` with a 4xx status.

### `POST create-order` (verify_jwt false; checks `apikey` header equals anon key is not required)

Request:
```json
{ "product": "burn", "text": "...", "wish_text": null, "recipient_name": null,
  "email": "optional@x.am", "lang": "hy", "show_on_stream": true, "consent": true }
```
**Since 0013** any paper product (`burn`, `burn_wish`, `gift`, `midnight`) → `400 PRODUCT_RETIRED` (checked first, before the other fields); only `light` orders are accepted (see "Light up Armenia"). The paper rules below describe the retired path.
Rules: `consent` must be true; `product` must be an active product (`burn` or `light`; others → `400 PRODUCT_UNAVAILABLE`); `text` 1–120 chars after trim and whitespace collapse; `wish_text` and `recipient_name` must be empty for `burn` (they belonged to the retired `burn_wish`/`midnight` and `gift`); email optional but must be valid if present (required when payments are disabled, so we can send the link at launch).
Moderation: blocklist hit → `400 TEXT_REJECTED`; likely personal names/phone numbers/links → order allowed but `moderation='hidden'` (never shown publicly); otherwise `pending`.
Rate limit: 8 orders per IP hash per 10 minutes → `429 RATE_LIMITED`.

Response:
```json
{ "code": "k7m2...", "amount_amd": 500, "status": "pending",
  "payment": { "mode": "redirect", "url": "https://bank/..." } }
```
`payment.mode` is one of `redirect` (go to `url`), `mock` (go to `url`, test only), `form` (Idram: build a `<form method="POST" action="{action}">` with one hidden input per entry of `fields` and submit it: `{ "mode": "form", "action": "https://...", "method": "POST", "fields": { "EDP_...": "..." } }`), `disabled` (status is `awaiting_launch`; we saved the paper and will email a payment link when payments open).
Moderation at creation: texts the automatic checks reject are `rejected`/`hidden`; everything else is `pending` and needs approval in the admin page before it appears publicly. Setting `AUTO_APPROVE=1` stores clean texts as `approved` directly (not recommended: the automatic filter misses spaced-out insults, phone numbers and names).

### `GET order-status?code=...`

Returns the buyer's own order: `{ code, status, product, amount_amd, burn_number, text, has_wish, recipient_name, created_at, paid_at, gift_share_amd }`. The wish itself is never returned (order links get shared); `has_wish` is a boolean (it is about the retired next-year wish, `wish_text`, not the wish in the fire). `gift_share_amd` is the gift_ledger amount once paid, else the floor(20%) the order will contribute. 404 if unknown.

### `POST start-payment`

`{ "code": "...", "lang": "hy" }` starts (or restarts) payment for an existing order in `awaiting_launch`, `pending` or `failed` (launch emails; someone else paying from the order link). Disabled provider: `{ code, status, payment: { mode: "disabled" } }`, nothing changes. Otherwise the order becomes `pending` and the response is `{ code, status, payment }` with the same `payment` shapes as create-order. 404 `NOT_FOUND`, 409 `ALREADY_PAID` / `ORDER_NOT_PAYABLE`, 400 `PRODUCT_UNAVAILABLE` (the order's product is no longer sold, e.g. a saved `burn_wish`; nothing changes). Rate limit 8 per IP hash per 10 minutes.

### Payment provider endpoints

- `GET/POST pay-return-ameria` — Ameriabank BackURL. Reads `orderID`/`paymentID`, calls `GetPaymentDetails` server-to-server, checks `ResponseCode == "00"` and amount, then `confirm_payment`, then 302 to the order page: `${SITE_URL}/p/{code}` for hy (root) and `${SITE_URL}/{en|ru}/p/{code}` otherwise (vercel.json must rewrite `/p/:code` to the static `/p/?c=:code` page).
- `POST pay-callback-idram` — Idram EDP precheck + result callback with checksum verification; answers `OK`.
- `GET pay-mock?code=...` — only when `PAYMENT_PROVIDER=mock`; confirms and redirects. Returns 404 otherwise.

### `POST join-waitlist`

`{ "email": "...", "lang": "hy" }` → `{ "ok": true }`. Rate limit 5 per IP hash per 10 minutes.

### `POST join-bloggers`

A blogger/influencer applies to come along on the December 31 gift delivery (film it, tell their audience).

Request:
```json
{ "name": "Anna", "link": "https://instagram.com/anna", "platform": "instagram", "audience": "25k",
  "email": "anna@x.am", "phone": "+374 91 123456", "message": "…", "lang": "hy", "consent": true }
```
Response: `{ "ok": true }` — the same for new and already-known emails (no enumeration; a repeated email adds another row).

Rules (text fields: NFC, invisible characters dropped, newlines/tabs and repeated whitespace collapsed to one space, trimmed; lengths in characters after that):
- `consent` must be exactly `true` → else `CONSENT_REQUIRED`.
- `name` required, ≤ 80 → `NAME_REQUIRED`.
- `link` required, ≤ 300 → `LINK_REQUIRED`; must be an `http://` or `https://` URL with a dotted host and no `user:password@` → `LINK_INVALID`. A link without a scheme (`instagram.com/anna`) gets `https://` prepended; other schemes (`javascript:`, `mailto:`, …) and bare handles (`@anna`) are `LINK_INVALID`.
- `platform` optional: `instagram` | `tiktok` | `youtube` | `facebook` | `telegram` | `other` (case-insensitive) → else `PLATFORM_INVALID`.
- `audience` optional free text ≤ 40 (e.g. `"25k"`; a number is accepted and stored as text).
- `email` required → `EMAIL_REQUIRED`, valid → `EMAIL_INVALID` (stored lower-case).
- `phone` optional, ≤ 30, digits with optional leading `+`, spaces, `()-.`, at least 5 digits → `PHONE_INVALID`.
- `message` optional, ≤ 500.
- `lang` `hy` | `en` | `ru`, default `hy`.
- Any length over its limit → `TOO_LONG` with `field` naming it: `{ "error": { "code": "TOO_LONG", "message": "...", "field": "name" | "link" | "audience" | "email" | "phone" | "message" } }`.

Checks run in this order, the first failure is returned: body (`INVALID_JSON`), consent, name, link, platform, audience, email, phone, message. All validation errors are 400. Rate limit 5 per IP hash per hour → `429 RATE_LIMITED` (invalid requests are not counted).

### `POST admin` (for `/admin/`)

Header `x-admin-token` must equal secret `ADMIN_TOKEN` (≥ 32 chars, else always 401). 10 failed attempts per IP hash per 10 minutes → 429. Body `{ "action": ... }`:
`stats` → `{ orders_by_status, revenue_amd, gift_fund_amd, waitlist_count, papers_burned, pending_moderation, lights_lit, lights_held, lights_cell_conflict, needs_refund, bloggers_count }`;

`moderate` `{ code, moderation: approved|hidden|rejected, reason? }`;
`moderate_wish` `{ code, moderation: approved|hidden|rejected, reason? }` — the order's wish in the fire (0013) → `{ ok, code, moderation }`, 404 `NOT_FOUND` for an unknown order or an order without a wish;

## Light up Armenia (the map)

A second product: a night map of Armenia split into exactly **111,111 plots** of 500×500 m (Lake Sevan excluded; generated by `tools/make_map.py` from Natural Earth). The map is fixed for this year and will not be extended. A person buys one free plot and places a light on it: an icon, a colour, a short message and an optional signature. The country gradually lights up. Plots are finite and first come, first served. 20% of every light goes to the gift fund, like papers.

### Products (`products` table and `site/config/site.json`)

| code | price | what |
|---|---|---|
| `light` | 500 | One plot with a light |
| `light_big` | — | **Not sold** (inactive since 0008). Was: same plot, a large glowing light. The code path (`big` in `get_map`/`get_cell`) stays and is always `0`/`false` for new lights. |

### Data

- `map_cells(id int pk, province text, town_index int)` seeded by `migrations/0004_cells_seed.sql` (regenerated by `tools/make_map.py` for the 111,111-plot map; several `INSERT` statements). id = row * 540 + col on a 540 × 537 grid, so ids are 0–289,979 (never ≥ 300,000); only 111,111 of the grid positions are plots. Province codes: yer ara arm ag kt gr sh lo tv vd su.
- New columns on `orders`: `cell_id int null references map_cells(id)`, `light_icon text null` (one of `tree home candle star gift pomegranate`), `light_color text null` (one of `amber red green white blue violet`), `light_signature text null` (≤ 30). For light products the order `text` is the light's message, **1–60 chars**. For paper products these columns must be null.
- `cell_holds(cell_id int pk references map_cells, order_id bigint not null references orders(id), expires_at timestamptz not null)`: a plot is taken when a hold exists with `expires_at > now()`. Paid lights have `expires_at = 'infinity'`.
- Lights do **not** get a `burn_number` and are **not** counted in `papers_burned` and **not** shown in `get_fire_feed`. Their one **wish in the fire** (0013, `fire_wishes`) does get a `burn_number` and is counted and shown (see "Wish in the fire").

### Reservation rules

- `create-order` (or `start-payment`) for a light product, when payments are open: atomically take the plot with `insert ... on conflict (cell_id) do update set order_id = excluded.order_id, expires_at = excluded.expires_at where cell_holds.expires_at < now()`; if no row results → `409 CELL_TAKEN`. Hold time 30 minutes.
- When payments are disabled (`awaiting_launch`) nothing is held; the order just saves the design and email.
- `start-payment` for a light: re-takes the hold for the same order (allowed if free or already held by this order); else `409 CELL_TAKEN`.
- On confirmed payment (inside `confirm_payment`): for light products set the hold to `infinity` for this order. If the plot is held by a different order (rare: hold expired and someone else took it), still mark the order paid, set `moderation_reason = 'cell_conflict'`, and leave it for the admin to move or refund.
- Refund (`admin_mark_refunded`): delete the plot hold of that order.
- Moderation: `text` and `light_signature` go through the same moderation as papers (signature may contain a name — that is the buyer's own signature, so names do not hide it; phone numbers, links, insults do). Public display needs `moderation = 'approved'`; otherwise the plot shows the light without text.

### RPCs for the browser (anon, SECURITY DEFINER)

- `get_map()` (packed since 0012) → `{ "lit_packed": "<base64>", "held_packed": "<base64>", "total": 111111, "lit_count": n, "by_province": {"yer": n, ...}, "warm": [[cell_id, warmth], ...], "updated_at": ... }`. `total` = number of rows in `map_cells` (111,111). `held` = plots currently reserved in an unexpired payment. `warm` (0011) = the 50 warmest lit rooms (see "Warmth and visits"). The JSON arrays `lit` and `held` of 0005–0011 are gone (with 100,000 lit plots they were 1.9 MB; packed: 535 KB, ~300 KB gzipped).

  **Packed format.** Both strings are standard base64 (alphabet `A–Z a–z 0–9 + /`, `=` padding, no line breaks); an empty list is `""`. Entries are sorted by `cell_id`, ascending, no duplicates.

  | field | bytes per plot | layout |
  |---|---|---|
  | `lit_packed` | 4 | `b0 = (id >> 16) & 255`, `b1 = (id >> 8) & 255`, `b2 = id & 255`, `b3 = (icon_index << 4) \| (color_index << 1) \| big` |
  | `held_packed` | 3 | `b0 b1 b2` as above |

  So `id = b0 << 16 | b1 << 8 | b2`, `icon_index = b3 >> 4`, `color_index = (b3 >> 1) & 7`, `big = b3 & 1`. `icon_index` / `color_index` are positions (0–5) in the icon and colour lists above; `big` is 0 or 1 (always 0 for new lights). Example: plot 4321, `star`, `red`, small → bytes `00 10 E1 32`. Reference decoder (pure TypeScript, usable in the browser): `supabase/functions/_shared/mappack.ts` (`decodeLitPacked`, `decodeHeldPacked`), pinned by `supabase/tests/mappack.test.ts`.
- `get_cell(p_cell_id int)` → `{ cell_id, province, town_index, status: "free"|"held"|"lit", icon, color, big, message, signature, lit_at, room, warmth, visits }` where message/signature are null unless approved, `room` is the plot's room layout (see "The room") when lit, else null (0010), and `warmth` / `visits` are the room's counters (integers, 0 when not lit or none yet; 0011).
- `get_public_stats()` gains `lights_lit`.

### Edge Functions

- `create-order` accepts `product: "light"` (`light_big` → `400 PRODUCT_UNAVAILABLE`) with body fields `cell_id`, `text` (message), `light_icon`, `light_color`, `light_signature` (optional), `room` (optional, see "The room"; absent or `null` = no room yet), `email`, `lang`, `consent`. Errors: `CELL_INVALID` (not an integer 0–299999, or not a map cell), `CELL_TAKEN`, `ICON_INVALID`, `COLOR_INVALID`, `SIGNATURE_TOO_LONG`, `SIGNATURE_REJECTED`, `TEXT_TOO_LONG` (for >60), `ROOM_INVALID`. For papers `room` must be absent or `null`, else `400 ROOM_NOT_ALLOWED`. `show_on_stream` is ignored for lights.
- `order-status` also returns `cell_id`, `light_icon`, `light_color`, `light_signature`, `province`, `town_index`, `room` (layout or `null`) and `fire` (the wish in the fire or `null`, 0013) for light orders.
- `burn-wish` (below) burns the light's one wish in the fire.
- `update-room` (below) changes a light's room.
- `room-warmth` (below) sends warmth to a lit room or counts a visit.
- Payment return for lights goes to the same paper page (`/p/?c=CODE`); the page shows the light instead of a paper.

### The room (3D room of a light, migration 0010)

Every light comes with a small decorated 3D room. The buyer arranges furniture in it; anyone who opens a lit plot can visit it (read-only, from `get_cell`). The layout is pure structured data (no free text), so it is **not moderated** and is shown for every lit plot.

Stored in `orders.room jsonb null` (lights only; a CHECK keeps it null for papers and bounds its shape and size).

Layout (validated strictly by `validateRoom` in `_shared/validation.ts`; anything else → `400 ROOM_INVALID`):

```json
{ "v": 1, "wall": "sage", "floor": "oak", "glow": true,
  "items": [["tree", 0, 0, 0], ["sofa", 3, 5, 2], ["cat", 7, 7, 3]] }
```

| key | value |
|---|---|
| `v` | the number `1` |
| `wall` | `cream` \| `sage` \| `night` \| `berry` |
| `floor` | `oak` \| `walnut` \| `tile` |
| `glow` | boolean (fairy lights on/off) |
| `items` | array of 0–40 `[type, x, z, r]`: `type` one of `tree tree_small sofa armchair table tv fireplace gifts rug lamp shelf plant piano snowman cat dog candles pomegranates radio clock`; `x`, `z` integers 0–7 (grid cell of the item's anchor); `r` integer 0–3 (rotation in quarter turns) |

- All five keys are required and no other keys are allowed (also none inside items: an item is exactly a 4-element array). Strings are matched exactly (case-sensitive, no trimming). Numbers must be JSON integers in range (`1.5`, `"1"`, `-1`, `8` are invalid; `-0` is stored as `0`).
- `JSON.stringify(room)` must be ≤ 4096 bytes (UTF-8); checked first, on the input as sent. A valid layout is at most ~1.1 KB, so this only stops junk.
- Item order is preserved. Footprint overlap is checked in the browser only; the server accepts two items on the same cell.
- The server stores (and returns) a canonical copy. Read-back key order is not guaranteed (jsonb), item order is.

#### `POST update-room` (verify_jwt false)

Request: `{ "code": "<order code>", "room": { ...layout } }` — the order code is the capability (as in `order-status` / `start-payment`). `room` is required (`null` → `ROOM_INVALID`); it replaces the whole layout.

Response: `{ "ok": true }`.

Errors (checked in this order): `400 INVALID_JSON` (body not a JSON object), `404 NOT_FOUND` (malformed code), `400 ROOM_INVALID`, `429 RATE_LIMITED` (60 per IP hash per hour; invalid requests are not counted), `404 NOT_FOUND` (unknown code), `409 ORDER_NOT_EDITABLE` (not a light order, or status is not `awaiting_launch`, `pending` or `paid` — i.e. `failed`, `cancelled`, `refunded` can't be changed). Plus the browser-endpoint codes (`403 ORIGIN_NOT_ALLOWED`, `405`, `413 PAYLOAD_TOO_LARGE` > 8 KB, `500 INTERNAL`).

Paid lights stay editable: the change shows up in `get_cell` immediately.

### Warmth and visits (migration 0011)

Visitors of a lit plot's room can **send warmth** (a heart) to its owner, once per visitor, and the page counts **visits**. Both numbers are public: `get_cell` returns `warmth` and `visits`, `get_map` returns `warm`, the 50 warmest rooms, for a "warmest rooms" list.

- Only **lit** plots count (a `cell_holds` row with `expires_at = 'infinity'` whose order is `paid`, the same test as `get_map`/`get_cell`). Free and held plots → `404 NOT_LIT`.
- One warmth per salted IP hash per room (`room_warmth_log` primary key `(cell_id, ip_hash)`). A second try changes nothing and answers the current count with `already: true`.
- Visits are best-effort: every call counts one visit (no de-duplication), up to the rate limit.
- The counters belong to the light, not the plot: if a plot is refunded and later lit by someone else, the new owner starts at 0 (old counts are hidden at once and reset on the next write).
- `get_map().warm`: `[[cell_id, warmth], ...]`, at most 50, lit plots with `warmth > 0` only, warmest first, ties by lower `cell_id`.

Data: `room_stats(cell_id pk → map_cells, order_id → orders (the light the counters belong to), warmth int ≥ 0, visits int ≥ 0, updated_at)`, `room_warmth_log(cell_id → map_cells, ip_hash (64 hex), created_at, pk(cell_id, ip_hash))`. RLS on, no policies, service role only. Service-role RPCs: `room_add_warmth(p_cell_id int, p_ip_hash text)` → `{ ok: true, warmth, already } | { ok: false, error: "NOT_LIT" | "INVALID_ARGS" }`; `room_add_visit(p_cell_id int)` → `{ ok: true, visits } | { ok: false, error: "NOT_LIT" }` (plus the internal helper `room_stats_prepare`).

#### `POST room-warmth` (verify_jwt false)

Request: `{ "cell_id": 4321, "action": "warm" }` or `{ "cell_id": 4321, "action": "visit" }`.

Responses (200):

```json
{ "ok": true, "warmth": 12, "already": false }   // warm, counted
{ "ok": true, "warmth": 12, "already": true }    // warm, this visitor already warmed this room (nothing changed)
{ "ok": true, "visits": 340 }                    // visit, counted
{ "ok": true }                                    // visit over the rate limit: nothing counted, no numbers
```

Rules and errors (checked in this order):
- `400 INVALID_JSON` — body is not a JSON object.
- `400 CELL_INVALID` — `cell_id` is not an integer 0–299999 (a string of up to 6 digits is accepted, as in `create-order`).
- `400 ACTION_INVALID` — `action` is not exactly `"warm"` or `"visit"`.
- Rate limit per IP hash (invalid requests above are not counted): `warm` 30 per hour → `429 RATE_LIMITED` (`Retry-After: 600`); `visit` 300 per hour → over it the answer is `200 { "ok": true }` (never 429).
- `404 NOT_LIT` — no such plot, or the plot is not lit.
- Plus the browser-endpoint codes (`403 ORIGIN_NOT_ALLOWED`, `405`, `413 PAYLOAD_TOO_LARGE` > 8 KB, `500 INTERNAL`).

Frontend: call `visit` once when a room opens; show `warmth`/`visits` from `get_cell` and update them from the `room-warmth` answer. After `warm`, show the heart as sent whether `already` is `true` or `false` (the visitor may have warmed this room before).

### Wish in the fire (migration 0013)

One payment (a `light`, 500 AMD) includes **exactly one wish burned in the shared fire** (the same fire and counter as the papers). The buyer writes it after paying — or already while the order is saved before payments open (`awaiting_launch`); such a wish is not public until the order is paid. No separate payment, no second wish for the same light.

Data: `fire_wishes(order_id pk → orders, text 1–120, show_on_stream bool default true, lang, moderation pending|approved|hidden|rejected default pending, moderation_reason, burn_number int unique from burn_number_seq, created_at)`. RLS on, no policies, service role only. Service-role RPC `burn_wish(p_code, p_text, p_show, p_lang, p_moderation, p_reason)` → `{ ok: true, already, burn_number } | { ok: false, error: "ORDER_NOT_FOUND" | "ORDER_NOT_LIGHT" | "ORDER_NOT_PAID" | "INVALID_ARGS" }` (locks the order row).

Public: in `get_fire_feed` as `product: "wish"` once the order is `paid` (refunded/cancelled orders drop out); `text_public` only when `show_on_stream` and `moderation = 'approved'`; counted in `get_public_stats.papers_burned`.

**Burn numbers.** A wish written on a paid order gets its number at once. A wish written on an `awaiting_launch` order gets a provisional number, and a **new** number when the order becomes paid (so it enters the fire after everything already burned; the live page polls with `after_number`). Always read the current number from `order-status`.

#### `POST burn-wish` (verify_jwt false)

Request:
```json
{ "code": "<order code>", "text": "...", "show_on_stream": true, "lang": "hy" }
```
- `code` — the light order's code (the capability, as in `order-status`); normalized like every code input (trim, lower-case, `i`/`l` → `1`, `o` → `0`).
- `text` — 1–120 characters after the paper normalization (NFC, invisible characters dropped, newlines/tabs and repeated whitespace → one space, trimmed).
- `show_on_stream` — optional, default `true`; only `false` turns it off (the wish still burns, without its text).
- `lang` — `hy` | `en` | `ru`, default `hy`.

Response (200):
```json
{ "ok": true, "burn_number": 1234, "already": false }   // saved now
{ "ok": true, "burn_number": 1234, "already": true }    // this order already has its wish: nothing changed, the text sent now is ignored
```

Errors (checked in this order; error shape `{ "error": { "code", "message" } }`):
- `400 INVALID_JSON` — body is not a JSON object.
- `400 CODE_INVALID` — `code` is not a well-formed order code.
- `400 TEXT_REQUIRED`, `400 TEXT_TOO_LONG` (> 120).
- `429 RATE_LIMITED` — 20 per IP hash per hour, 10 per order code per hour (invalid requests above are not counted; `Retry-After: 600`).
- `400 TEXT_REJECTED` — blocklist hit (as for papers); nothing saved. Contact data or names are accepted but stored `hidden` (never public); everything else is `pending` until approved in admin (`approved` directly only with `AUTO_APPROVE=1`).
- `404 ORDER_NOT_FOUND` — no order with this code.
- `409 ORDER_NOT_LIGHT` — the order is not a light (e.g. an old paper).
- `409 ORDER_NOT_PAID` — the order's status is not `paid` or `awaiting_launch` (`pending` = payment in progress: retry after the payment page; `failed`, `cancelled`, `refunded`).
- Plus the browser-endpoint codes (`403 ORIGIN_NOT_ALLOWED`, `405`, `413 PAYLOAD_TOO_LARGE` > 8 KB, `500 INTERNAL`).

#### `order-status` → `fire`

For light orders `order-status` returns `fire`:
```json
"fire": { "burn_number": 1234, "text": "...", "show_on_stream": true, "created_at": "2026-12-31T19:00:00Z" }
```
or `"fire": null` when no wish was written yet. `text` is what the code holder wrote (the same person already sees the order's own `text`); the moderation state is not returned. Paper orders have no `fire` key.
