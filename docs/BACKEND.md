## Products and prices

One price since `0008_single_price`: **500 AMD**, 20% (100 AMD) to the gift fund.

| code | price | active | notes |
|---|---|---|---|
| `burn` | 500 | yes | a paper burned in the fire |
| `light` | 500 | yes | a light on the map |
| `burn_wish` | 1900 | **no** | not sold; row kept for old orders |
| `gift` | 900 | **no** | not sold; row kept for old orders |
| `midnight` | 2900 | **no** | not sold; row kept for old orders |
| `light_big` | 4900 | **no** | not sold; row kept; code path (`big`) kept but unreachable |

The `products` table is the source of truth for charging; `site/config/site.json` is only what the frontend shows and must match. `create-order` and `start-payment` refuse an inactive product with `400 PRODUCT_UNAVAILABLE` (start-payment: a saved `awaiting_launch` order of a retired product can no longer be paid; nothing changes). 0008 also re-prices unpaid saved lights (`awaiting_launch`/`failed`) to 500; `pending` ones keep their amount because a bank payment may be open. To sell a product again: `update products set active = true, price_amd = … where code = …;`.

## Migrations

With the Supabase CLI (from the repo root):

```sh
supabase link --project-ref maqcaowpfhmqcavboszy
supabase db push            # applies supabase/migrations/* not yet applied
```

Or paste a migration file into the dashboard SQL editor. Migrations are plain SQL and are written to be applied once, in order.

### Apply order

```
0001_init → 0002_payment_attempts → 0003_admin → 0003a_map_cells → 0004_cells_seed → 0005_lights → 0006_needs_refund → 0007_revoke_pg_net → 0008_single_price → 0009_bloggers → 0010_rooms → 0011_room_warmth
```

0001 and 0002 are live. Apply the rest **in this order**, each file as one transaction (SQL editor, or MCP `apply_migration` with the file's name). 0004 inserts into `map_cells` (created by 0003a), 0005 needs both 0003 (it replaces `admin_stats`, `admin_list_orders`, `admin_mark_refunded`) and the plots, 0006 replaces `admin_stats` again. 0008 needs 0005 (the `light`/`light_big` rows). 0009 replaces `admin_export` (0003) and `admin_stats` (0006) with `create or replace`, keeping everything they returned. 0010 (after 0009) adds `orders.room` and replaces `get_cell` (0005) with `create or replace`, keeping everything it returned and its grants. 0011 (after 0010) adds `room_stats`/`room_warmth_log` and the two service-role RPCs, and replaces `get_cell` (0010) and `get_map` (0005) with `create or replace`, keeping everything they returned and their grants.

**Supabase CLI caveat:** `supabase db push` only picks up files named `<digits>_name.sql`, so it **skips `0003a_map_cells.sql`** and 0004 then fails (`relation "public.map_cells" does not exist`). Apply these files by hand in the order above (SQL editor or MCP `apply_migration`).

Safe to re-run? 0004 (`on conflict do nothing`), 0007 (`revoke`), 0008 (plain `update`s) yes; the others are apply-once (`create table`/`add column`/`create function`).

Security model, enforced by 0001:
- RLS is enabled on every table with **no** policies, and `anon`/`authenticated` have no table or sequence privileges at all.
- Default privileges for objects created by `postgres` in `public` no longer grant anything to `anon`/`authenticated`/`PUBLIC`: any future browser RPC needs an explicit `grant execute`.
- Browser-callable: `get_public_stats()`, `get_fire_feed(after_number, max_rows)`, `get_map()`, `get_cell(p_cell_id)` (SECURITY DEFINER, `search_path = public`).
- `service_role` only: `confirm_payment`, `check_rate_limit`, `begin_payment_attempt`, `hold_cell`, `peek_rate_limit`, `release_rate_limit`, `admin_*`, `room_add_warmth`, `room_add_visit`, `room_stats_prepare` (0011). Tables `room_stats` and `room_warmth_log` (0011): RLS on, no policies, `service_role` only. Table `blogger_applications` (0009) follows the `waitlist` model: RLS on, no policies, no `anon`/`authenticated` privileges, `service_role` only.
- An order becomes `paid` only in `confirm_payment`, which locks the order row, checks provider, amount and payment id, is idempotent (same payment → `already: true`; a second, different payment for a paid order → `ORDER_PAID_BY_OTHER_PAYMENT`, needs a manual refund; one payment id can never pay two orders), assigns `burn_number` from `burn_number_seq`, writes the floor(20%) `gift_ledger` row and sets `paid_at`.

Security advisor: the remaining notices are intentional — `rls_enabled_no_policy` (INFO, by design) and `anon/authenticated_security_definer_function_executable` (WARN) for exactly the four public RPCs the contract requires (`get_public_stats`, `get_fire_feed`, `get_map`, `get_cell`).

## Secrets

Set in Dashboard → Edge Functions → Secrets, or:

```sh
supabase secrets set --project-ref maqcaowpfhmqcavboszy \
  PAYMENT_PROVIDER=disabled SITE_URL=https://<site> ALLOWED_ORIGINS= ALLOW_VERCEL_PREVIEWS=1 ALLOW_LOCALHOST=1 \
  IP_HASH_SALT=<64 hex chars> ADMIN_TOKEN=<random, >= 32 chars> AUTO_APPROVE=0
```

| Secret | Default when unset | Notes |
|---|---|---|
| `PAYMENT_PROVIDER` | `disabled` | `disabled` \| `mock` \| `ameria` \| `idram`; unknown values → `disabled` |
| `SITE_URL` | `https://example.invalid` | used for redirects and CSV links; its origin is always CORS-allowed (unless `.invalid`) |
| `ALLOWED_ORIGINS` | empty | comma-separated; `https://*.example.am`-style wildcards allowed. **Empty = `SITE_URL`'s origin only** (never `*`; nothing at all while `SITE_URL` is the `.invalid` placeholder) |
| `ALLOW_VERCEL_PREVIEWS` | off | `1` also allows any `https://*.vercel.app` origin (preview deployments) |
| `ALLOW_LOCALHOST` | off | `1` allows `http://localhost:*`, `127.0.0.1`, `[::1]` |
| `IP_HASH_SALT` | derived from the service-role key | set a real one; changing it only resets rate-limit counters |
| `AUTO_APPROVE` | `0` | only `1` stores clean texts as `approved` at creation; otherwise they are `pending` until approved in admin (papers and light messages/signatures alike). The blocklist still rejects, contact data/names still hide. |
| `ADMIN_TOKEN` | unset → admin always 401 | must be ≥ 32 chars; rotate by setting a new value |
| `AMERIA_CLIENT_ID`, `AMERIA_USERNAME`, `AMERIA_PASSWORD`, `AMERIA_API_BASE` | — | all four required for `ameria`; test base `https://servicestest.ameriabank.am/VPOS` |
| `IDRAM_ACCOUNT_ID`, `IDRAM_SECRET_KEY` | — | required for `idram` |
| `IDRAM_ACTION_URL` | `https://banking.idram.am/Payment/GetPayment` | override only if Idram says so |

If `PAYMENT_PROVIDER` names a provider whose secrets are missing, `create-order` / `start-payment` answer `503 PAYMENT_MISCONFIGURED` (fail closed, nothing is saved).

## Switching the payment provider

1. Set the provider's secrets, then `PAYMENT_PROVIDER=ameria` (or `idram`). Secrets apply to new function instances within seconds; no redeploy needed.
2. Saved papers (`awaiting_launch`) are paid through `POST start-payment { code, lang }` — export them with admin `awaiting_launch_csv` and email each buyer their link. The export also lists saved orders of retired products (`burn_wish`, `gift`, `midnight`, `light_big`; see the `product` column): their links answer `PRODUCT_UNAVAILABLE`, so contact those buyers separately (e.g. invite them to burn a new paper).
3. To test end-to-end without a bank: `PAYMENT_PROVIDER=mock`. `create-order` returns `payment.mode = "mock"` with a `pay-mock?code=…` URL that marks the order paid and redirects. **Never leave `mock` on in production** — anyone could mark their own order paid.

### `payment` shapes (create-order and start-payment)

```json
{ "mode": "disabled" }
{ "mode": "mock",     "url": "https://…/functions/v1/pay-mock?code=…" }
{ "mode": "redirect", "url": "https://servicestest.ameriabank.am/VPOS/Payments/Pay?id=…&lang=am" }
{ "mode": "form", "action": "https://banking.idram.am/Payment/GetPayment", "method": "POST",
  "fields": { "EDP_LANGUAGE": "AM", "EDP_REC_ACCOUNT": "…", "EDP_DESCRIPTION": "Order 100001",
              "EDP_AMOUNT": "500", "EDP_BILL_NO": "100001", "EDP_EMAIL": "…" } }
```

`form` (Idram): build `<form method="POST" action="{action}">` with one hidden `<input name value>` per field and submit it. Idram returns the buyer to static SUCCESS/FAIL URLs set in its merchant cabinet, which do not carry our code: the frontend should remember the order code (e.g. `localStorage`) before submitting and show `/p/{code}` afterwards.

Redirects after payment go to `${SITE_URL}/p/{code}` (hy) or `${SITE_URL}/{en|ru}/p/{code}`; `vercel.json` needs a rewrite from `/p/:code` (and `/en/p/:code`, `/ru/p/:code`) to the static `/p/?c=:code` page.

Rate limits (per salted IP hash, fixed 10-minute windows unless noted): create-order 8, start-payment 8, join-waitlist 5, join-bloggers 5 per **hour**, update-room 60 per **hour**, room-warmth `warm` 30 / `visit` 300 per **hour** (separate counters), order-status 120, admin failed logins 10, pay-return-ameria 60, pay-callback-idram 60.

Admin login limiter: every admin request first counts against `admin_fail:<ip_hash>` with `check_rate_limit` (atomic, so parallel guesses can't exceed 10), then the token is compared in constant time; a correct token gives its count back with `release_rate_limit` (0006).

Bank endpoints: the Idram limit is per caller IP, and Idram calls from a few server IPs (precheck + result = 2 calls per payment), so 60/10 min is ~30 Idram payments per 10 minutes. Raise `LIMITS.idramCallback` in `_shared/ratelimit.ts` before a busy launch night.

## Moderation

`_shared/moderation.ts`, lists in `_shared/moderation-data.ts` (edit there; matching rules are documented at the top of the file).
- Blocklist (strong profanity/slurs in Armenian script, Armenian Latin/Cyrillic transliteration, Russian, Russian translit, English) in `text`, `wish_text` or `recipient_name` → `400 TEXT_REJECTED`; in a light's `light_signature` → `400 SIGNATURE_REJECTED`. Nothing saved.
- Phone numbers, URLs/domains, emails, `@handles`, or a common Armenian first name (three scripts, with case endings and `-յան/-yan/-ян`) in `text`/`wish_text` → saved with `moderation='hidden'`, `moderation_reason='auto:<kind>'`. Never shown publicly.
- `light_signature`: contact data → `hidden` (`auto:signature_<kind>`); first names do **not** hide it (it is the buyer's own signature).
- Otherwise `approved` (only with `AUTO_APPROVE=1`) or `pending` (default).
- Public text appears in `get_fire_feed` only when `show_on_stream` **and** `moderation='approved'`. On the map a paid light is always lit; `get_cell` returns its message and signature only when `moderation='approved'` (`get_map` never carries text).

## Privacy in `payment_events`

Every bank request is logged **before** processing. What the caller sent (Ameria return parameters, Idram callback fields) is first reduced to a whitelist — `EDP_*`, `orderID`, `paymentID`, `resposneCode`/`responseCode`, `opaque`, each value cut to 200 characters (`_shared/callbacks.ts`) — and bodies over 8 KB are refused (413). Then everything (also the bank's own GetPaymentDetails answer) passes through `_shared/sanitize.ts`: masked card numbers, cardholder/client names, expiry, CVV, card-binding ids, emails, phones and IP addresses (`ip`, `ProcessingIP`, …) are dropped; `EDP_PAYER_ACCOUNT` is stored only as `sha256:<salted hash>`. Amounts, codes, ids, statuses and timestamps are kept.

pay-return-ameria calls GetPaymentDetails only when `opaque` is an existing order code or `orderID` is one of our payment attempts (an order's `provider_order_num` or an `init` event's `OrderID`).

A confirmed payment for an order already paid by a different payment (`ORDER_PAID_BY_OTHER_PAYMENT`, and a checksum-valid Idram result for such an order) writes a `payment_events` row of kind `needs_refund`; admin `stats` shows the count as `needs_refund`. Find them: `select * from payment_events where kind = 'needs_refund' order by created_at desc;`

## Light up Armenia (the map)

Contract: `docs/ARCHITECTURE.md` "Light up Armenia". What the backend does:

- **Data.** `map_cells` (0003a + 0004, 7,048 plots). `orders` gains `cell_id`, `light_icon`, `light_color`, `light_signature`; CHECKs: all four null for papers; cell/icon/colour required for `light`/`light_big` (`light_big` is no longer sold since 0008; the CHECKs keep covering it for old rows); icon/colour from the fixed lists; signature 1–30; `text` 1–60 for lights and 1–120 (unchanged) for papers; lights never have a `burn_number` (`orders_paid_complete` no longer requires one for them). `cell_holds(cell_id pk, order_id unique, expires_at)`; deleting an order deletes its hold.
- **Holding a plot.** `hold_cell(order_id, cell_id, minutes=30)` (service_role) locks the order, checks it is a payable light order for that plot, then `insert … on conflict (cell_id) do update … where expires_at < now() or (same order and not infinity)`; returns whether this order now holds the plot. Two orders racing for one plot: exactly one gets `true` (tested with two sessions).
- **create-order** (light): validate → rate limit → moderation (`SIGNATURE_REJECTED` when only the signature is bad) → price from `products` → `get_cell` (`null` → `CELL_INVALID`, not `free` → `CELL_TAKEN`) → insert. Payments open: `hold_cell`; if it lost a race the order is set `cancelled` and the answer is `409 CELL_TAKEN`. Payments disabled: no hold (`awaiting_launch`, design + email saved). `show_on_stream` is stored `false`.
- **start-payment** (light): after the status checks and before `begin_payment_attempt`, `hold_cell` re-takes the plot (free, expired, or already this order's) or answers `409 CELL_TAKEN`. With payments disabled nothing changes (as for papers).
- **confirm_payment**: lights get no burn number (`burn_number: null`); the hold becomes `infinity` (taking the plot if it is free or expired). If another order holds it, the order is still paid, `moderation_reason = 'cell_conflict'`, result `cell_conflict: true` → admin moves (`update orders set cell_id = … ; update cell_holds …`) or refunds. Admin `stats.lights_cell_conflict` counts them.
- **Refund** (`admin_mark_refunded`) deletes the order's hold: the plot is free again.
- **Public.** `get_map()` — one SQL statement, `lit` = `[cell_id, icon_index, color_index, big]` arrays sorted by id, `held` = unexpired unpaid holds, `total` = rows in `map_cells`, `by_province` = lit counts for all 11 provinces (zeros included). Locally with 7,001 lit plots: ~20 ms, 133 KB JSON. `get_cell(p_cell_id)` → `null` for a non-plot; `big` is a boolean; `icon/color/lit_at` only when lit; `message/signature` only when lit and approved. `get_public_stats` gains `lights_lit`; `papers_burned` and `get_fire_feed` cover papers only.
- **order-status** adds `cell_id`, `light_icon`, `light_color`, `light_signature`, `province`, `town_index`, `room` for light orders (`text` is the message, `burn_number` null).
- **Rooms (0010).** `orders.room jsonb null`: the light's 3D room layout (contract: ARCHITECTURE.md "The room"). CHECKs `orders_room_light_only` (null for papers) and `orders_room_shape` (object, `v = 1`, `items` array ≤ 40, text form and stored size ≤ 8192 bytes — a backstop; the strict 4096-byte / lists / ranges check is `validateRoom`). `create-order` stores an optional room for lights; `update-room` `{code, room}` replaces it while the order is `awaiting_launch`/`pending`/`paid` (conditional `update … where status in (…)`, so a refund racing with it wins → 409). `get_cell` returns `room` for lit plots. No moderation (no free text). Inspect: `select code, status, room from orders where room is not null order by id desc limit 20;`
- **Warmth and visits (0011).** `room_stats(cell_id pk, order_id, warmth, visits, updated_at)` and `room_warmth_log(cell_id, ip_hash, created_at, pk(cell_id, ip_hash))` (contract: ARCHITECTURE.md "Warmth and visits"). `room_stats_prepare` finds the plot's paid light, upserts and locks its `room_stats` row (`for update`, so concurrent calls for one room serialize) and, when the row belongs to an earlier light of that plot, resets it to 0 and deletes the plot's warmth log. `room_add_warmth` inserts into the log `on conflict do nothing` and adds 1 only when a row was inserted. `get_cell`/`get_map` join `room_stats` on the current light's `order_id`, so a previous owner's counts never show. Inspect: `select s.*, o.code from room_stats s left join orders o on o.id = s.order_id order by warmth desc limit 20;`
- **admin**: `stats` gains `lights_lit`, `lights_held`, `lights_cell_conflict` (and `needs_refund`, 0006; `bloggers_count`, 0009); `papers_burned` is papers only. `list_orders` rows include the light fields; `q` also searches signatures.

Operations:

```sql
-- Who holds / lit a plot
select h.*, o.code, o.status, o.product from cell_holds h join orders o on o.id = h.order_id where h.cell_id = 4321;
-- Paid lights that lost their plot
select code, cell_id, paid_at from orders where status = 'paid' and moderation_reason = 'cell_conflict';
-- Expired holds are harmless (ignored everywhere); to tidy up:
delete from cell_holds where expires_at < now();
```
